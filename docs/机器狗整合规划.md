## 2. 现有系统 A：语音 + LLM 控狗（已跑通）

### 2.1 核心链路
```
人声 → 狗麦克风 → Opus 上传 → FunASR(本地ASR) → qwen3.8-flash(阿里云MaaS,走7890代理)
     → EdgeTTS(合成) → Opus 下发 → 狗扬声器
                                 ↓ 识别到动作意图
                          robot_action → POST http://10.1.56.231/control → 狗做动作
```

### 2.2 你写的关键文件
- `xiaozhi-server/plugins_func/functions/robot_action.py`
  - function_call 工具：LLM 识别到动作意图后调用，向 `http://10.1.56.231/control` 发 HTTP POST。
  - **move 类**（前进/后退/左转/右转）：持续运动，默认 1.5s 后自动补发停止指令 `{"move":"S"}`，上限 5.0s（防止"一直走不停"）。
  - **action 类**（预置姿势）：鞠躬=2、摇摆=4、握手=7、戳戳=8、伸懒腰=9、前跳=10、收腿=12。
  - 狗离线不阻断对话链路。
- `web-control/`：网页调试台（连 WS 发文本/语音指令、快捷动作按钮），无真机时调试用。
- `启动.bat`：一键拉起后端(WS 8000 / OTA 8003) + 前端(8080)，自动探测带 funasr 的 Python、加 ffmpeg 到 PATH、查端口占用。
- `机器狗启动指南.md` / `ESP-Hi-机器狗探索记录.md`：部署与"接管"文档。

### 2.3 运行期配置（重点：活配置在 `data/.config.yaml`，不是 `config.yaml`）
- `xiaozhi-server/data/.config.yaml` 是覆盖配置，含：
  - `LLM: QwenLLM`（qwen3.8-flash，阿里云 MaaS，base_url 走 `llm-p3vxs7hqk42wx4oq.cn-beijing.maas.aliyuncs.com`）
  - `prompt`：机器狗可爱人设，强制多动作一次性放进 `actions` 列表

## 3. 现有系统 B：电脑视觉识别（同事给，半成品）

### 3.1 位置与形态
- 目录：`xiaozhi-esp32_视觉/tools/vision_control/`
- 一个 PC 端 Python 程序（`vision_dog.py` 为主入口），用**电脑摄像头**做人/手势识别。
- 验证情况（来自该目录 `.workbuddy/memory`）：selftest 29 项全过；MediaPipe / YOLO 两后端实机摄像头各 12s **零误触发**；`probe_image.py` 真实推理端到端可用。
- 运行环境：conda `D:\study_files\conda\envs\vision`（Python 3.13，mediapipe 1.0.1 + ultralytics 8.4.166）。

### 3.2 处理流水线
```
电脑摄像头(cv2) → 检测后端(MediaPipe 33点 / YOLO11-Pose 17点映射成33点布局)
   → 动作规则(action_rules.py) → 指令闸门(command_gate.py: 防抖/边沿触发/冷却)
   → 下发(emitter.py)
```

### 3.3 下发层（emitter）—— 这是整合的关键
- **默认 `DryRunEmitter`**：只往控制台打印 MCP 报文，**不真驱狗**。
- `--ws ws://<狗IP>:8080/ws`：`WebSocketEmitter`，把报文发到设备端本地 WebSocket 控制服务。
- 发出的指令格式（严格对齐固件 `mcp_server.cc`）：
  ```json
  {"jsonrpc":"2.0","id":<数字>,"method":"tools/call",
   "params":{"name":"self.dog.walk","arguments":{"steps":4,"speed":1000,"direction":1}}}
  ```
- **注意**：`id` 必须是数字；指令词是 `self.dog.walk/turn/sit/stand/stretch/shake/stop`，参数带 `steps/speed/direction`——这是照着 **`eda-robot-pro` 板子**的 MCP 工具设计的。

### 3.4 触发姿势对照表（同事定义）
| 姿势 / 手势 | 指令 | MCP 工具 |
|---|---|---|
| 双手向两侧上方举过头 | 前进 | `self.dog.walk(direction=1)` |
| 只举左手 | 左转 | `self.dog.turn(direction=1)` |
| 只举右手 | 右转 | `self.dog.turn(direction=-1)` |
| 双臂平举成 T 字 | 停止 | `self.dog.stop()` |
| 双手抱头 / 下蹲 | 坐下 | `self.dog.sit()` |
| 张开手掌 | 站立 | `self.dog.stand()` |
| 竖大拇指 | 伸展 | `self.dog.stretch()` |
| 剪刀手 | 摇摆 | `self.dog.shake()` |

优先级：全身姿势 > 手部手势。单目摄像头无深度，**词表里没有"后退"**。

### 3.5 同事明确写的"还没做"
> 固件侧 WebSocket 通道（把 `otto-robot/websocket_control_server` 搬到 `eda-robot-pro` + `CONFIG_HTTPD_WS_SUPPORT=y`）尚未完成，做完后 `--ws ws://<狗IP>:8080/ws` 才能真驱狗。

也就是：**同事这套现在只能"看"，还不能"动"；而且它预设的驱动方式（WS + eda-robot-pro）和你的狗（HTTP /control + ESP-Hi）根本不是一回事。**

## 4. 整合缺口分析 —— 为什么"合不起来"

| # | 维度 | 系统 A（你的狗） | 系统 B（同事视觉） | 冲突 |
|---|---|---|---|---|
| 1 | **传输协议** | HTTP `POST /control` | MCP over WebSocket `:8080/ws` | 协议不同，对不上 |
| 2 | **动作词表** | `{"action":"7"}` / `{"move":"F"}` | `self.dog.walk(steps=4,...)` | 词表与参数格式不同 |
| 3 | **目标板/固件** | ESP-Hi（仅 `/control`，动作有限） | 假设的 `eda-robot-pro`（含 WS 控制服务、动作丰富） | 板子与固件能力不同 |

补充缺口：
- **动作丰富度不对等**：同事的 坐下/站立/伸展/摇摆 在 ESP-Hi 上没有同名动作，只有有限的预设 ID（2/4/7/8/9/10/12），需要"就近映射"。
- **"后退"不可实现**：单目无深度，视觉侧本来就没做后退；而 `robot_action` 虽然支持后退，但视觉识别给不出这个信号。

## 5. 最终需求整合重述

> **让一只没有摄像头的 ESP-Hi 机器狗，用电脑摄像头充当它的"眼睛"，与已跑通的语音 + LLM 控狗能力整合，形成由同一套逻辑、同一个控狗通道统一驱动的智能机器狗系统。**

系统应有两条并存的"感官"输入通道，最终都落到同一只狗上：
- **听觉/语言通道（已具备）**：人说话 → 后端 ASR/LLM → `robot_action` → 狗动作。
- **视觉/体感通道（待接入）**：电脑摄像头拍到人 → 识别姿势/手势 → 狗动作。

"利用电脑摄像头代替机器狗的视觉"可拆成两层（需在落地时明确优先级）：
- **层 A（同事主目标，推荐先做）**：视觉→动作。人做手势/姿势，狗直接做对应动作。同事代码已具备识别能力，只差"真驱狗"这一步。
- **层 B（可选升级）**：视觉→语义。把电脑摄像头帧喂给后端 VLLM，让狗能"看见"并用语言描述/回应场景（"我看见你拿了个杯子"）。这才是"代替机器狗视觉"的完整体验，但需改后端图像注入，工作量更大。

## 6. 推荐整合方案（翻译层）

**原则**：不碰固件、不引入新硬件，复用已验证的 `/control` 通道，把两个系统的"出口"统一。

**做法**：在 `vision_control` 中新增一个 **HTTP 下发器**（类比已有 `DryRunEmitter` / `WebSocketEmitter`），加参数如 `--http http://10.1.56.231`，负责把 `self.dog.*` MCP 调用翻译成 ESP-Hi 能懂的 `/control` 报文，逻辑直接复用 `robot_action.py` 的映射思路（move 类走 1.5s 自动停止，action 类用预设 ID）。

映射草案：
- `self.dog.walk(direction=1)` → `{"move":"F"}`（前进）；`direction=-1` → 后退（ESP-Hi 支持，但视觉侧暂不触发）
- `self.dog.turn(direction=1)` → `{"move":"L"}`（左转）；`direction=-1` → `{"move":"R"}`（右转）
- `self.dog.stop()` → `{"move":"S"}`（停止）
- `self.dog.sit/stand/stretch/shake` → 映射到最接近的 ESP-Hi 预设（需确认：摇摆=4、握手=7、伸懒腰=9、前跳=10、收腿=12、鞠躬=2、戳戳=8；坐下/站立/伸展无直接对应，需产品决策）

**为什么选这条路线**：
- 零固件改动，风险最低、最快见效；
- 视觉通道和语音通道都走同一个 `/control` 出口，天然"统一驱动同一只狗"；
- 与同事已验证的识别/闸门逻辑完全解耦，只改最末端的"下发"环节。

## 7. 可选升级路线（层 B：VLLM 场景理解）

把 PC 摄像头帧通过后端既有 VLLM 通道注入，使 LLM 能基于"看到的画面"作答。需要：
- 在后端/前端侧建立"电脑端图像源 → 设备图像帧"的注入机制（xiaozhi 协议支持设备侧图像帧，但本机无设备摄像头，需由 PC 端代发）；
- 调整 prompt，让模型在适当时机调用视觉能力描述环境。
这条路线建议在层 A 跑通后再评估。

## 8. 待拍板事项 / 风险

1. **先做到哪一层？** 建议先层 A（手势→动作）跑通真驱狗，层 B 作二期。
2. **动作词表怎么对齐？** 只保留 ESP-Hi 能做的（前进/转向/停止 + 有限预设姿势），还是愿意为更丰富的视觉动作去刷/换 `eda-robot-pro` 固件？

4. **环境依赖**：视觉侧依赖 `D:\study_files\conda\envs\vision`（含 torch/mediapipe/ultralytics），与主控后端的 Python 环境不同，启动时需分别激活/指定解释器。
