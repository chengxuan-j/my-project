## 0. 先说需要改动的结论

设计文档方向是对的，六条契约与三条独立管线都成立。但**实读代码后有 5 处必须先处理的前提问题**，其中 1 处是硬阻塞：

| # | 问题 | 严重度 | 处理 |
|---|---|---|---|
| P1 | **M0 没有语料**。`storage/companion.db` 里 `conversations = 0`、`memories = 0`，只有 1 条 account + 1 条画像。设计文档 M0 说"读历史对话 → 跑提取 prompt"，但历史对话不存在 | 🔴 阻塞 | 新增前置任务 **M-1：造语料**（详见 §5.0） |
| P2 | **两套表结构 + 测试走同步路径**。`db/legacy.py:_SCHEMA`（同步 SQLite，`init_db` 建表，dev/test 用）与 `db/models.py`（SQLAlchemy ORM，`init_async_db` create_all）。`tests/*.py` 只调 `init_db()` | 🟠 高 | 四张新表**两处都要加**，否则测试与 dev 同步链路看不到表（§4.2） |
| P3 | **落库通道不一致**。现有记忆写入走同步 `get_conn()`；而 M3 列表 / M5 编排 / M6 日报 / 调度任务全部是异步 ORM。混用会导致一个 request 里两套连接 | 🟠 高 | 新模块统一走 **async ORM + `story_repo`**；提取器只做 LLM、落库交给 service（§4.3） |
| P4 | **画像里没有结构化 `people`**。设计文档 M3 依赖"people 关联 profile 人物 → 规则引擎推算时间"，但画像只有 `family: ["女儿小芳"]`、`life_experience: [...]` 这类字符串数组，没有人物实体表 | 🟡 中 | M3 降级为"基于现有画像字段的保守推算"，或另立 people 抽取小任务（§5.3） |
| P5 | **自查询接口不接受路径传 user_id**。设计文档写 `GET /api/v1/stories/{user_id}`，但现有 `/api/v1/*` 全部从 JWT 取 `user_id`（`chat.py:72` 有明确注释"不可伪造"） | 🟡 中 | 老人端一律用 token 身份；家属端走 `/family/elderly/{id}/...` + 绑定校验（§4.4） |

> 结论：**先做 M-1（造语料）再进 M0**，其余 4 条在 M1 建表阶段一次性落定。

## 2. 三条管线的落位

### 2.1 数据流（标注真实文件）

```text
POST /api/v1/chat                       app/api/v1/chat.py
   │
   ├─[既有] _extract_and_save ────────► MemoryExtractor → long_memory      （不动）
   │
   └─[新增] _extract_and_save_story ──► StoryExtractor                    （新）
              ├─ is_life_story=false → 丢弃
              └─ true → story_repo.create(status=draft)                   （新）
                          │
                          ├─ gap_detector.detect() → elicitation_queue    （新）
                          │
        ┌─────────────────┼──────────────────────────────┐
        ▼                 ▼                              ▼
  老人端确认卡        追问时机决策                    家属端时代轴
  StoryConfirmCard   elicitation.py                  StoryTimeline
  （M2, 老人 token） （M4, 仅 low 风险）              （M6, 绑定校验）
        │                 │                              │
        └─ archived ──────┴──────────────────────────────┘
                          │
                          ▼
              storyboard.build() → story_compilations                   （M5）
                          │
                    status=prompt_ready（止步，不调任何视频 API）
```

### 2.2 三条管线互不阻塞的证据

- **落库**：提取只写 `life_stories`，与 `long_memory` 物理隔离 → 事实记忆挂了不影响故事，反之亦然。
- **确认**：只在老人端 token 下操作（`require_elderly`）→ 家属端接口永远不触碰 `pending_confirm`。
- **编排**：读 `archived` 快照，不写回故事表 → 编排失败不影响已归档故事。
- **全链路降级**：LLM 不可用 → 提取静默跳过（照抄 `memory_extractor` 的 `LLMError` 分支）→ `/chat` 无感。

## 3. 契约 → 代码强制点对照

六条契约不能只写在文档里，每条都要有一个「代码里关不掉的地方」：

| 契约 | 强制点 | 具体实现 |
|---|---|---|
| 1 老人本人确认 | **接口角色门禁** | `confirm` / `discard` 挂 `Depends(require_elderly)`，且校验 `story.elderly_user_id == account.user_id`；家属路由无此二接口 |
| 2 默认 family / 创伤强制 private | **写入侧规则 + 读取侧过滤 + 不可回改** | 写入侧：`story_repo.set_visibility()` 遇 `visibility_locked=True` 直接 return，忽略入参；置锁条件 `emotion_tone == 创伤` 或 `avoid_flag`。读取侧三道（**过滤都在服务端，不是前端隐藏**）：① 家属时间轴只查 `archived` 且 `visibility ∈ (family, public)`；② 照片走**鉴权读接口** `/memoir/media/{id}`，按「老人本人 / 已绑定家属 且 故事当下可见」判定，不挂 StaticFiles（否则 private 照片变成"知道 URL 就能看"）；③ 编排快照在家属读取那一刻按**当下**可见集合再过滤每段镜头，整片被收回则 404 |
| 3 克制的追问 | **决策层硬门禁 + 默认不问** | `elicitation.should_elicit()`：**三道硬门禁全部通过**（`risk_level == "low"` / 本会话 `session_asks < MEMOIR_MAX_ASKS_PER_SESSION`（默认 1）/ 候选位于冷却期外）**且至少命中一个正向信号**（`is_first_turn_of_day` / 当前轮长度相对近期均值明显变长 / 与某个未补齐故事主题相关）才开口。「本会话」定义为 **30 分钟空闲窗口**（`SESSION_IDLE_MINUTES`）。任一条件不满足即返回 `None`，宁可漏问不可打扰 |
| 4 第一人称旁白、优先原话 | **编排 prompt 约束 + 后校验** | `storyboard` 生成后校验 `perspective` 默认 `first_person`；旁白回退判据是 **`introduces_third_person()`——模型是否引入了老人原话里没有的第三人称指代**（如"她十六岁那年…"），命中即整句回退老人原话；另叠一道相似度下限兜底。**不使用"必须含『我』"作为判据**（中文主语省略是常态，会把原话误判为非第一人称） |
| 5 不纠正记忆偏差 | **表结构 + 接口约束** | `raw_dialogue` 只允许 INSERT/追加，禁止任何 UPDATE 路径；偏差只写 `time_confidence`，无"纠正"接口。M6 家属唯一能写的对象是**照片**：`attach_photo()` 只新增 `story_media` 一行，**不碰** `raw_dialogue` / `summary` / `visibility`（`test_upload_does_not_touch_story_content` 直接断言这四项） |
| 6 不调视频/图像 API | **状态机 + 代码检查 + 探针验收** | `status` 枚举不含 `rendering` 的可达路径；`render_engine` / `video_url` 恒 `None`、响应带 `rendered=False`；单测断言无出网生成调用；`storyboard_probe.audit()` 逐条断言 `prompt_package` 内无任何视频/图片产物路径 |

## 4. 数据模型落地

### 4.1 ORM 表（`app/db/models.py`）

按设计文档字段实现，几个落地约定：

- `raw_dialogue` / `era_tags` / `people` / `source_msg_ids` / `story_ids` / `prompt_package` 用 SQLAlchemy `JSON`（PG 下自动 JSONB）。
- `time_type`、`emotion_tone`、`status`、`visibility`、`gap_type`、`perspective` 用 `String` + **应用层枚举校验**（不引 PG ENUM，保持 SQLite/PG 双兼容）。
- 时间字段用 `DateTime` + `func.now()`，与现有表一致。
- 索引严格按设计文档三条：`(elderly_user_id, status)`、`(elderly_user_id, era_tags)`、`(elderly_user_id, status, cooldown_until)`。

> ⚠️ `era_tags` 在 SQLite 下是 JSON 文本，`era_tags` 上的索引实际**只在 PG(JSONB)生效**。SQLite 下改为走 `(elderly_user_id, status)`，时代轴聚合在应用层做（数据量本就小）。

### 4.2 建表路径（P2 的处理）

```text
三处同时落，缺一不可：

1. app/db/models.py          ← ORM 模型（生产 + 异步路径，create_all 自动建）
2. app/db/legacy.py _SCHEMA  ← CREATE TABLE IF NOT EXISTS ×4
                                （dev 同步链路 + tests 的 init_db() 靠它）
3. scripts/ 无需迁移脚本     ← 4 张全是新表，无 ALTER，create_all 足够
```

- 现有 `legacy.py:_migrate()` 只用于"已有表加列"。本次没有加列，**不需要迁移脚本**——设计文档里"新增四张表的迁移脚本放 scripts/"这一步可省，改成上面两处即可（`alembic` 虽在依赖里但仓库无 `alembic/` 目录、无 `env.py`，本阶段不引 Alembic）。
- 验收断言：新库跑 `init_db()` 后，`sqlite_master` 里能查到 4 张 story 表。

### 4.3 落库通道（P3 的处理）

```python
# app/repositories/story_repo.py —— 全异步，与 family.py / scheduler 一致
class StoryRepo:
    def __init__(self, session: AsyncSession): ...
    async def create_draft(...) -> LifeStory
    async def list_by_status(elderly_id, status) -> list[LifeStory]
    async def set_status(story_id, status) -> bool
    async def set_visibility(story_id, visibility) -> bool   # 锁定时直接 return False
    async def append_raw(story_id, fragment) -> None          # 只追加
```

分工与现有代码保持一致（`MemoryExtractor` 只做 LLM、`MemoryManager` 负责写）：
- `StoryExtractor.extract()` → 纯 LLM，返回 dict，**不碰数据库**
- `app/memoir/story_service.py`（或直接在路由里）→ 拿 dict 调 `StoryRepo` 落库

### 4.4 接口设计（P5 的处理）

设计文档里 `/stories/{user_id}` 一律去掉路径身份：

| 场景 | 接口 | 门禁 |
|---|---|---|
| 老人看自己的待确认 | `GET /api/v1/stories/pending` | `require_elderly`，user_id 取 token |
| 老人确认/弃用 | `POST /api/v1/stories/{id}/confirm` \| `/discard` | `require_elderly` + 归属校验 |
| 老人视角回忆录 | `GET /api/v1/memoir/timeline` | `require_elderly` |
| 家属视角回忆录 | `GET /api/v1/family/elderly/{id}/memoir` | `require_family` + `list_elderly` 校验（照抄 `family.py:90` 范式） |
| 照片上传 | `POST /api/v1/memoir/stories/{id}/media` | 老人 `require_elderly`；家属走 family 前缀 |
| 编排 | `POST/GET/DELETE /api/v1/memoir/compilations[...]` | 归属校验 |
| 可见性 | 家属端响应**只返回** `status=archived AND visibility IN (family, public)` | 服务层过滤，非前端过滤 |

> 归属校验写成 `story_repo.get(story_id, elderly_user_id=...)` 的仓储方法，避免每个路由重复写 if。

## 5. 里程碑细化

### 5.0 M-1 · 造语料（新增，前置阻塞）

**为什么必须做**：M0 的"人工标注 50 条"和提取 prompt 调参都需要真实语料，而库里 `conversations = 0`。

- 写 `scripts/seed_demo_conversations.py`：为 `elderly_001`（王阿姨/纺织厂）生成 ~60 轮对话，覆盖
  - 情感锚点：1968 进纺织厂、车间机器声、同批工友老王、后来调动、退休、女儿小芳
  - 干扰项：寒暄、天气、今天吃啥、一次性情绪（用来测 precision）
  - 时代锚点：上山下乡、知青、票证年代
  - 人物/地点：老王、小芳、黑龙江/纺织厂/车间
- 直接 `INSERT` 进 `conversations`（复用 `short_memory` 表结构），带 `current_topic`
- **验收**：`SELECT count(*) FROM conversations WHERE user_id='elderly_001'` ≥ 60，且人工读一遍确认"像真老人说的"
- **产出**：语料 + 一份人工标注文件 `backend/data/story_eval_labels.jsonl`（50 条，标 `is_life_story` 真值）

**估算**：1 人日（含标注）

## 9. 决策（已定稿）

四个决策点均采纳「先轻后重」方案，理由与代价记录如下。

### D1 · 语料来源 → 脚本造为主 + 留出集

**做法**：脚本造 60 轮到 `elderly_001`，结构为 **40 条正例 + 20 条干扰**（含边界样本）；另留 **15~20 条风格不同的 holdout**，只做验收、不参与调参。

**理由**：M0 验收线是 precision ≥ 0.8，需要**真值精确、正负例比例可控**的集合。脚本造才能主动塞入"像生平其实是闲聊"的干扰项——这是 precision 最易崩的地方；真人语料难标注、量也凑不齐。

**代价 / 风险**：语料风格同质会让提取器过拟合、precision 虚高 → 故必须留 holdout 检验"没见过的样本"。将来有真人语料需再补一轮回归。

### D2 · Alembic → 不引

**做法**：靠 `init_async_db` 的 `create_all` + `legacy.py _SCHEMA` 两处建表；在 `models.py` 留 TODO 注释。

**理由**：仓库**无 `alembic.ini`、无 `alembic/` 目录**（`alembic` 仅是 `pyproject.toml` 里的空依赖）；4 张全是新表，`create_all` 已足够；且 dev 并行跑 legacy `init_db()`，再叠 Alembic 会让"表由谁创建"更难追踪。

**触发升级**：出现「给已有表加列/改类型」或上生产 PG 需版本化时，手写一次 baseline。

### D3 · people 结构化 → 字段照存，实体表缓建

**做法**：`life_stories.people` JSON 字段在 **M1 就要存**（提取 prompt 本就输出）；M3 时间推算先用「people × 画像 `family`/`life_experience` 字符串」弱匹配。

**理由**：建 `story_people` 实体表 = 必须做实体消解（"老王"/"王师傅"/"王哥"是否同一人），是独立难题，会拖住 M3。

**触发升级**：M0 报告显示具名人物密度高（>40% 故事含具体人名）→ 单独立 people 抽取任务。

### D4 · 时代轴定义 → 预置词表 + LLM 兜底

**做法**：新建 `backend/data/era_lexicon.json`，用**与 `music.json`/`stories.json` 相同的加载方式**（`app/content/` 读取）。词表给「规范名 + 同义词」，例：

```
知青时期  ← 上山下乡 / 插队 / 支边 / 插队落户
票证年代  ← 粮票 / 布票 / 凭票供应
```

LLM 只做两件事：把口语锚点**归一**到词表项；未命中则自由生成并标 `unmapped`。

**理由**：纯 LLM 会让标签**漂移**（今天"知青岁月"、明天"上山下乡时期"），时代轴分组碎裂且不可测。

**代价**：一次性维护 20~30 条词表。

### 追加项 · `memoir_enabled` 功能开关

新增 `memoir_enabled: bool = False`（dev 默认关），对齐现有 `digest_enabled` / `scheduler_enabled` 写法。用途：**暗发布**——代码合入后 `/chat` 行为与调度任务均不受影响，等 M0 数据出来再打开。

### D5 · 追问上限与冷却天数 → 1 问 / 3 天（M4 收尾时定稿）

这两个值直接决定"老人被问几次"，不能拍脑袋。用真语料 60 轮回放逐档测（`scripts/elicitation_probe.py`）：

| 会话上限 | 冷却 1 天 | 冷却 3 天 | 冷却 7 天 | 冷却 14 天 |
|---|---|---|---|---|
| 1 问 | 5 次（8.3%） | **5 次（8.3%）** | 5 次 | 5 次 |
| 2 问 | 9 次（15.0%） | **10 次（16.7%）** | 10 次 | 10 次 |
| 3 问 | 13 次（21.7%） | **11 次（18.3%）** | 11 次 | 11 次 |

**结论**：

- **`MEMOIR_MAX_ASKS_PER_SESSION = 1`**。1→2 让追问频率**直接翻倍**（8.3% → 16.7%），而 2→3 只多一次（瓶颈已经不在上限，而在正向信号本身）。契约3 是"主动追问但克制"，翻倍那一档太贵，取 1。
- **`MEMOIR_GAP_COOLDOWN_DAYS = 3`**。3 天与 7/14 天结果**完全一致** → 说明 3 天已足够挡住重复追问，再拉长只是让缺口永远问不到；1 天则会多放行 1 次。取 3 是"够严的最小值"。

> **踩坑记录（探针自身）**：这个探针最初把 `max_asks_per_session=1` / `cooldown_days=3` **写死在代码里**，
> 于是无论怎么改环境变量，输出都一模一样——它其实只在测"常数等于常数"。
> 拿这种结果去定产品取值等于自欺。已改为从 `get_settings()` 读，并在输出里回显当前取值。

> 决策汇总：D1 脚本造+holdout｜D2 不引 Alembic｜D3 存字段缓建表｜D4 词表+LLM｜D5 追问 1 问/冷却 3 天｜追加 `memoir_enabled` 开关。

### ✅ M4 缺口追问（已完成）

**设计取向**：这一层要解决的不是"怎么问"，而是**要不要问**。老人陪伴产品里，一个不合时宜的追问比不问伤害大得多——老人会觉得"这机器在查我"。所以默认答案是**不问**，只有明确的绿灯才放行。

| 产物 | 说明 |
|---|---|
| `app/memoir/elicitation.py` | 决策层：三道门禁 + 三个正向信号 + 回避识别 + 账本收口 |
| `app/memoir/story_service.py` | `ingest()` 里接上 `close_asked_gaps`：老人补上了某类信息就关掉同类缺口 |
| `app/memory/memory_manager.py` | `build_context` 新增 `_resolve_elicitation()`，只做**预选**不记账；结果放 `ChatContext.elicitation` |
| `app/companion/prompts.py` | `_elicitation_block()`：把 `follow_up_hint` 交给主模型**化成家常问句**，明确禁止照搬字面措辞、禁止提"记录/回忆录/档案" |
| `app/api/v1/chat.py` | `_finalize_memoir()`：生成**成功之后**同步收尾（回避处理 + 追问记账） |
| `app/scheduler/jobs/story_gap_scan.py` | 夜间批量记账（冷却到期放回 / 已补齐关闭 / 过期放弃），已注册进 `scheduler_manager` |

**三道硬门禁**（任一不满足 → `None`，没有例外）：`risk_level != "low"` ｜ 本会话已问满 `MEMOIR_MAX_ASKS_PER_SESSION` ｜ 没有过 cooldown 的候选。

**三个正向信号**（至少命中一个才放行；不是"满足即可问"，是"有理由才问"）：`day_opening`（当天第一句）｜ `paused`（回复明显变短且情绪平稳）｜ `relevant`（正好聊到那条时代/地点/人物）。

**三个开发中的关键决定**（都由实测或契约倒逼）：

1. **「本会话」= 30 分钟空闲窗口，不是自然日**。老人上午聊完、下午又来，是两段对话，不该因为"今天已经问过"被封口一整天。实现上就是"最近 30 分钟内问过几次"。
2. **记账放在生成成功之后，且同步执行（不用后台任务）**。放在生成前，一旦生成失败额度就被占掉，老人这一晚再也等不到那个问题；放后台则老人连发两条消息可能被问两次——**那正是这个上限要防的事**。代价是几毫秒，换契约确定性。
3. **`draft`/`pending_confirm` 之外没有新增状态**：回避走 `avoid_flag` + `visibility_locked`（复用契约2 的锁），不引入新的枚举。

**真语料回放验收**（`scripts/elicitation_probe.py`，75 个缺口、60 轮回放）：

```text
实际开口：5 次 / 60 轮（8.3%）
  拦下  40 次：session_limit      ← 硬上限在连续对话里确实咬得住
  拦下  13 次：无正向信号          ← "默认不问"确实生效
  拦下   2 次：risk_level         ← 命中语料里的创伤轮次
手工场景 ✅ 高风险不问 ✅ 问满不问 ✅ 无候选不问 ✅ 无理由不问 ✅ 回避后永久锁定
克制性（开口次数 ≤ 轮数/10）：通过
```

> **回放踩到的两个坑（都已修，且值得记住）**：
> ① 探针最初**从没写过 `conversations` 记录**，而 `is_first_turn_of_day` 是查库推出来的——查不到上一条就永远判定"今天第一次开口"，结果 58/60 轮都在追问。改成**按生产时序**：决策时当前轮还没落库，决策后再写。
> ② 只推进时钟不管节奏时，60 轮被压成一段连续对话，报告只剩"上限生效了"一个信息。改成一轮 3 分钟、每 20 轮隔天，才看得到跨天节奏。
> **一处已知的模拟失真**：语料里每轮 `topic` 与该轮故事 `title` 同源，所以 `relevant` 在回放里恒为真——报出的开口次数应视为**下界**。

**三个开发中修正的设计**：

1. **「必须含『我』」是错的判据**。真语料探针直接打脸：3 段旁白被判"非第一人称"，可它们**就是老人原话**（「那时候买米买面都得要粮票…」）——中文主语省略是常态。同时 `她十六岁那年离开了家` 这种真·第三人称改写反而能靠相似度蒙混过关。改成判**「模型是否引入了老人原话里没有的第三人称指代」**：既不再误杀省略主语句，又能真的抓住违约。
2. **时长不采信 LLM**：模型给的秒数加起来永远不等于 60，这次多 3 秒下次少 5 秒，前端进度条就没法对齐。响应里同时给出 `total_seconds`（实际）与 `requested_seconds`（请求），段数太少顶到每段 25 秒上限时**如实告知短了**，不假装凑够。

> **修法**：不碰全局缓存，只把 `media_service` 命名空间里的 `get_settings` 换成固定 stub（作用域严格限制在该文件）。
> 这条"整套测试依赖 lru_cache 先被填成 `:memory:`"的前提是隐式约定，动 `DATABASE_URL`/缓存前务必留意。

**顺带修掉的两个小问题**：① 四个探针都在漏临时库（`cleanup()` 在进程退出前 unlink，Windows 上句柄还占着 → 异常被吞），已集中修为**先 `dispose_engine()` 再删**，验证后零残留；② 老人端回忆录加载文案「正在翻您的旧账本」改成「正在翻您的老照片」（"旧账本"读着像记账）。
